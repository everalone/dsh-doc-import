# ADR 0001: 文档内容以内联文本进入对话，而非核心 DocumentBlock

- 状态：**已被 [ADR 0002](./0002-document-file-reference.md) 取代**（2026-09-04 实测后改为纯文件引用）
- 日期：2026-09-04

## 背景

DSH 的附件管线（`dsh-attachment` / `dsh-llm`）目前只把光栅图片（PNG/JPEG/WebP/GIF）
作为一等附件投影给模型；txt/pdf/docx 等文档没有内容块类型，用户只能复制路径到聊天里，
再靠模型用本地文件工具读取，体验割裂。

## 决策

插件在 host 端把文档解析为文本，提交时以 `[document 文件名 (类型, 页数/字符数, id: sha256)]`
头内联进用户消息正文；扫描版 PDF 逐页 OCR 后合并进同一文本。原文件与提取全文存入插件私有
存储（`~/.dsh/storages/doc-import/<sha256>/`），`read_document` 工具按 id 回读全文。

## 备选方案

1. **泛化核心附件管线**：新增 `DocumentBlock` 内容块类型，让文档像图片一样成为一等附件。
   - 优点：附件语义完整（角色无关、路由投影、预算控制都在核心层）。
   - 缺点：需要 fork/PR harness 本体，随版本升级持续维护；开发周期长。
2. **只做模型工具**：仅注册 `read_document` 工具读本地路径。
   - 优点：最快。
   - 缺点：不解决"复制路径"的痛点，模型可能不主动调用。

## 后果

- 文本进入消息正文，任何模型都能读取，会话历史与重启天然可回读。
- token 成本随文档大小线性增长；用 1M 字符内联上限 + 50k 字符费用提示 + 超限截断来护栏。
- 大文档被截断后依赖模型主动调用 `read_document` 回读，存在"拖进去了但没读全文"的可能。
- 若将来核心出现 DocumentBlock，本插件的解析器与存储可直接迁移，内联头格式保持稳定即可。
