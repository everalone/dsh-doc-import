# ADR 0003: 浏览器端草稿为全局状态并跨重载持久化，而非按会话隔离

- 状态：已采纳
- 日期：2026-09-10

## 背景

早期实现把待发送的文档草稿当作**会话局部状态**：文档卡片坞监听 `sessionId` 变化，
一旦切换会话就 `clearAllDrafts()`，理由是"避免把 A 会话的文档误带进 B 会话的消息"。

真实事故（用户报障 + 会话日志实证）：用户贴入文档 → 卡片显示"已就绪" → 切到新对话发问
→ 发出的消息里**没有引用行**，模型只能回答"我没有看到你贴进来的文档"。用户的实际工作流
恰恰是"先贴文档，再开新对话问它"，被这条规则直接破坏。

第二条触发路径同样致命：草稿只存在内存（模块级数组），**页面刷新或客户端模块 HMR 重载**
会把它整个重置——开发期每次重建 client 包都会触发。

引用行是模型获知文档存在的唯一线索，草稿丢失对用户表现为"文件根本没发出去"，且无从察觉。

## 决策

1. 草稿是**浏览器全局**状态：跨会话可见、可发送；**只在发送成功后**清除已就绪项
   （`clearReadyDrafts()`）。
2. **禁止**任何"会话切换即清空草稿"的逻辑；该 API（`clearAllDrafts`）已删除，并由
   `test/client-state.test.mjs` 锁死不得回归。
3. 草稿镜像到 `sessionStorage`（`state.ts` 的 `toPersistedDrafts` / `rehydrateDrafts`）：
   只存 `id / 名称 / 类型 / 页数 / 字符数 / status / 引用行 / 费用摘要`，**不存提取正文**；
   重载后 ready 项立即可用，`parsing` / `ocr` 中的项自动续接状态轮询（结果按页持久化，
   不重复计费）。

## 备选方案

1. **按会话隔离但保留（切回即恢复）**：用户"贴完就开新对话"的工作流仍会失败，且需要
   按会话索引草稿 + 额外的"文档在另一个会话"提示；复杂度更高而收益不明。
2. **仅内存全局（不持久化）**：跨会话能用，但刷新或 HMR 重载即丢——开发期高频触发，
   等于把同一个事故换了个触发条件。

## 后果

- 文档可能被从**另一个**会话发出（跨会话可见的代价）。缓解：卡片在任何会话都可见、
  可单点移除，用户不会在无感知的情况下带上一份文档。
- `sessionStorage` 不落盘到仓库、不携带正文，隐私与体积风险可控；记录数上限 20 条。
- 发送后清 ready 项 + 镜像同步清空，避免"上次的文档"残留到下一次发送。
